## Система с высоты птичьего полёта

`yandex-wiki-search-mcp` — MCP-сервер перед публичным HTTP API Яндекс Вики:
32 тулзы (10 на чтение, 22 на запись), 2 ресурса, три транспорта (stdio,
streamable HTTP, SSE) и один опциональный OAuth-слой для многопользовательских
HTTP-деплоев.

Вызов тулзы проходит такой путь:

```
MCP-клиент
  │  stdio / streamable-http / sse
  ▼
MCPServer (mcp_wiki/mcp/server.py)
  │  middleware: DEBUG-лог таймингов → запрос прячется в contextvar
  ▼
tool handler (mcp_wiki/mcp/tools/*)
  │  параметры через pydantic → get_yandex_auth() с per-request переопределением
  ▼
WikiClient (mcp_wiki/wiki/custom/client.py)
  │  заголовки ← select_org(); ретраи с бэкоффом; маппинг ошибок
  ▼
https://api.wiki.yandex.net
```

Ответ возвращается типизированной pydantic-моделью, сериализуется без
`None`-полей, валидируется по output-схеме тулзы и дублируется текстовым
блоком, чью подробность регулирует `TOOL_RESULT_TEXT`.

## Два слоя

Пакет разделён на доменный слой и слой представления, и зависимость между ними
направлена строго в одну сторону:

- **`mcp_wiki/wiki/`** — домен Яндекс Вики. Асинхронный HTTP-клиент, модели
  ответов, таксономия ошибок, работа со слагами. Ничего не знает про MCP;
  обязан быть пригоден из обычного скрипта (и пригоден —
  `scripts/contract_sweep.py` использует его напрямую).
- **`mcp_wiki/mcp/`** — MCP-представление. Сборка сервера, тулзы, ресурсы,
  модели параметров, OAuth. Свободно импортирует Wiki-слой.

**Правило: `mcp_wiki.wiki` никогда не импортирует из `mcp_wiki.mcp`.** Это не
эстетика: одно нарушение однажды замкнуло цикл импортов через
`mcp_wiki.wiki.__init__`, из-за которого `import mcp_wiki.mcp.utils` падал с
`ImportError` при первом импорте, а тесты этого не видели, потому что
conftest уже импортировал пакет в рабочем порядке. `tests/test_imports.py`
импортирует каждый модуль в сабпроцессе, чтобы держать слоистость честной.
Если хелпер нужен обеим сторонам, он живёт в Wiki-слое, а `mcp_wiki.mcp.utils`
его реэкспортирует (прецедент — `normalize_slug`).

## Карта кода

### Точка входа и конфигурация

- **`mcp_wiki/__main__.py`** — собирает `Settings`, отказывается стартовать при
  подозрении на опечатку в окружении (см. ниже), настраивает логирование в
  stderr, логирует эффективную конфигурацию, затем
  `create_mcp_server(settings).run(transport, **run_options(settings))`.
- **`mcp_wiki/settings.py`** — pydantic-settings поверх переменных окружения и
  `.env`-файла. Два решения, которые стоит знать:
  - `extra="ignore"`: `.env` — директорная конвенция, общая с другими
    инструментами, поэтому посторонний `OPENAI_API_KEY` не должен
    останавливать этот сервер.
  - `suspicious_env_keys()`: защита от опечаток, которую раньше давала
    строгость, — починенная и расширенная на настоящие переменные окружения.
    Ключ внутри неймспейсов этого сервера (`WIKI_*`, `OAUTH_*`, `REDIS_*`,
    `MCP_*`, `TOOL_*`), difflib-близкий к реальному полю (`WIKI_READ_ONL`),
    останавливает старт с подсказкой did-you-mean; посторонние ключи
    (`REDIS_URL`) проходят.
  - Модельный валидатор следит за инвариантами: ровно один из
    `WIKI_ORG_ID`/`WIKI_CLOUD_ORG_ID`, токен, пока OAuth выключен,
    OAuth-тройка, когда включён. `include_local_uploads` — property, а не
    поле: `page_upload_attachment` читает файловую систему *сервера*, поэтому
    предлагается только вне многопользовательских OAuth-деплоев.

### MCP-слой

- **`mcp_wiki/mcp/server.py`** — точка сборки. `create_mcp_server()` подключает
  lifespan, опциональные OAuth-провайдер и стор, инструкции, кэш-хинты,
  middleware, кастомные роуты (`/healthz`, OAuth-коллбэк), затем регистрирует
  ресурсы и тулзы. Три детали, которые кусаются:
  - `WikiMCPServer.call_tool` постобрабатывает результаты для
    `TOOL_RESULT_TEXT` (`pretty`/`compact`/`none`), не трогая structured
    content.
  - Транспортные kwargs живут в `run_options()`/`http_app_options()`, а не в
    конструкторе — и **`host` обязан до них доходить**: SDK по умолчанию
    ставит loopback и автоматически взводит защиту от DNS rebinding, которая
    за настоящим hostname отвечает `421` на каждый MCP-запрос, пока `/healthz`
    продолжает говорить `200`.
  - `server_version()`/`server_description()` читают метаданные пакета, так
    что `pyproject.toml` остаётся единственным источником обоих.
- **`mcp_wiki/mcp/context.py`** — `AppContext`, полезная нагрузка lifespan:
  экземпляр `WikiProtocol` плюс базовый веб-URL.
- **`mcp_wiki/mcp/middleware.py`** — DEBUG-лог каждого входящего сообщения со
  временем обработки. Намеренно молчит на INFO: строка на каждый запрос
  подвесила бы stdio-сервер, чей клиент не вычитывает stderr.
- **`mcp_wiki/mcp/request_ctx.py`** — contextvar с транспортным запросом
  обрабатываемого сообщения. Существует потому, что SDK не инжектит `Context`
  в ресурс со статическим URI, а `wiki-mcp://configuration` нужна
  query-строка. `Server.middleware` апстримом помечен как provisional, поэтому
  этот модуль и `middleware.py` — сознательно единственные два места, которые
  его трогают.
- **`mcp_wiki/mcp/params.py`** — общие `Annotated`-типы параметров (ID, слаги,
  курсоры, `fetch_all`), модели тел запросов для операций с гридами и
  `build_instructions()`, которая выводит инструкции сервера из тех же
  настроек, что управляют регистрацией тулзов, — read-only сервер описывает только
  то, что зарегистрировал.
- **`mcp_wiki/mcp/utils.py`** — `get_yandex_auth()` (per-request
  переопределение токена и организации; предпочитает `Context` обработчика,
  откатывается на запрос из middleware) и `resolve_page_locator()` (контракт
  «ровно один из `page_id`/`slug`», общий для всех страничных тулзов).
- **`mcp_wiki/mcp/resources.py`** — два ресурса: `wiki-mcp://configuration`
  (сообщает пару организаций через тот же `select_org()`, что и клиент,
  поэтому не может отчитаться комбинацией, которую не несёт ни один запрос) и
  `wiki-mcp://yfm-cheatsheet`.
- **`mcp_wiki/mcp/tools/`** — `page_read.py` (10 читающих тулзов),
  `page_write.py` (22 пишущих; регистрируются только при
  `WIKI_READ_ONLY=false`, а `page_upload_attachment` — только при выключенном
  OAuth), `common.py` (резолв локатора через живой API, когда слаг должен
  стать id или наоборот). Пишущие тулзы прикладывают неблокирующие
  `yfm_warnings` из `mcp_wiki/yfm.py`.
- **`mcp_wiki/yfm.py`** — YFM-линт без зависимостей (только предупреждения,
  никогда не блокирует запись) и текст шпаргалки. Правила кодируют живое
  поведение рендерера (`scripts/yfm_smoke.py`).

### OAuth-подсистема (`mcp_wiki/mcp/oauth/`)

Опциональна; собирается только при `OAUTH_ENABLED=true`. Сервер тогда
выступает OAuth authorization server для MCP-клиентов и проксирует реальную
идентичность в Яндекс OAuth:

```
клиент → /authorize ──► редирект на oauth.yandex.ru (ключ: серверный state_id)
Яндекс → /oauth/yandex/callback ──► обмен кода, выпуск нашего кода, редирект клиенту
клиент → /token ──► наш код → пара access/refresh токенов Яндекса, хранится хэшированной
```

- **`provider.py`** — поток выше. Ключ хранения pending-авторизации всегда
  генерирует сервер (`secrets.token_hex`); клиентский `state` — данные,
  которые эхом возвращаются на финальном редиректе, и никогда не ключ.
  Нарушение этого правила было CVE-образным: предсказуемый ключ позволял
  атакующему перезаписать pending-запись и забрать код жертвы, включая PKCE.
- **`store.py`** — протокол `OAuthStore` и общий `REFRESH_TOKEN_TTL_SECONDS`
  (31 день, срок жизни refresh-токена Яндекса).
- **`stores/memory.py`** — dict-стор для однопроцессных деплоев. Раз
  `/authorize` и `/register` не аутентифицированы, всё истекаемое несёт
  дедлайн, а записи запускают амортизированный sweep (порог перенацеливается
  на удвоенный выживший размер), так что брошенные логины не могут раздувать
  процесс безгранично.
- **`stores/redis.py`** — продакшн-стор: хэшированные ключи, шифрование на
  уровне полей (`crypto.py`, версионированные ключи для ротации через
  `OAUTH_ENCRYPTION_KEYS`), TTL делегированы Redis. Регистрации клиентов
  истекают вместе с `client_secret_expires_at`, который SDK проставляет на
  `/register` (`OAUTH_CLIENT_SECRET_EXPIRY_SECONDS`).
- **`types.py`** — pydantic-формы записей state, callback и кода.

### Wiki-слой (`mcp_wiki/wiki/`)

- **`proto/pages.py`** — `WikiProtocol`, интерфейс, против которого
  программируют тулзы. Тулзы никогда не видят `WikiClient` напрямую; тесты
  подставляют `AsyncMock` с поверхностью этого протокола.
- **`proto/common.py`** — `YandexAuth` (per-request учётные данные) и
  `select_org()`: per-request auth заменяет организацию **целиком**, никогда
  не смешивая `cloud_org_id` запроса с серверным `org_id`. Клиент строит из
  него заголовки, а ресурс конфигурации из него же отчитывается, так что
  разъехаться они не могут.
- **`proto/types/pages.py`** — модели ответов. `BaseWikiModel` выбрасывает
  `None`-поля при сериализации (экономия токенов в выводе для LLM) и вычищает
  шум `title` из генерируемых JSON-схем; `DynamicWikiModel` вдобавок сохраняет
  неизвестные ключи при round-trip. Формы ячеек/строк/колонок гридов тоже
  живут здесь.
- **`custom/client.py`** — `aiohttp`-клиент. Единая воронка `_request()`
  применяет auth-заголовки (схема `OAuth`/`Bearer`, IAM или per-request
  токен), заголовки организации через `select_org()`, ретраит идемпотентные
  сбои (экспоненциальный бэкофф с equal jitter, `Retry-After` уважается до
  потолка, гридовый `409 CONFLICTING_OPERATION` ретраится как лок, а не
  ошибка) и маппит сбои в таксономию ошибок. Также владеет многошаговыми флоу:
  upload-сессии (create → parts → finish → attach) и поллинг отложенной
  операции `page_clone`.
- **`custom/errors.py`** — таксономия. `WikiError` → `WikiApiError`
  (HTTP-уровень, `build_api_error()` выбирает подкласс; `GridConflict` для
  гридового лока) плюс `PageNotFound`/`GridNotFound`, `WikiOperationError`
  (отложенная операция провалилась *после* того, как каждый HTTP-обмен
  удался), `WikiTransportError` (таймауты и сбои соединения, с непустым
  сообщением даже для `TimeoutError`), `WikiConfigError` (кривая настройка
  сервера).
- **`custom/slugs.py`** — `normalize_slug()`: полный URL Вики или слаг → голый
  слаг. Живёт здесь, потому что клиенту он нужен на каждом страничном вызове
  (см. правило слоёв).
- **`custom/anchors.py`** — вставка по якорю для `page_append_content`
  (заголовок `{#id}`, инлайн-якоря, простые заголовки).

## Один контракт API, на который стоит обратить внимание

`GET /pages/descendants?slug=` с **пустым** слагом означает «вся организация» —
осознанный контракт API, а не небрежная обработка ввода (неразрешимый слаг
даёт 404; пропуск параметра — 400). Проверено вживую 2026-08-10, см.
[api-notes_ru.md](api-notes_ru.md). `page_get_descendants(from_root=true)` —
единственный, кто его шлёт. Не «чините» пустой слаг в
`WikiClient.page_get_descendants`; `resolve_page_locator` по-прежнему отклоняет
его для всех остальных тулзов, где API действительно нужна страница.

## Тестирование

Тесты используют моки на каждом шве, который задаёт архитектура:

| Шов | Техника |
|---|---|
| MCP-протокол ↔ тулзы | in-memory `Client` из SDK против настоящего `MCPServer`; тулзы видят `AsyncMock` `WikiProtocol` |
| тулзы ↔ Wiki-клиент | контракт — `WikiProtocol`; у пишущих тулзов проверяются точные аргументы вызовов |
| Wiki-клиент ↔ HTTP | `aioresponses`; ассерты на заголовки, query-параметры и тела в том виде, как их отправил бы aiohttp |
| OAuth ↔ Redis | `fakeredis` |
| пакет ↔ интерпретатор | `tests/test_imports.py` импортирует каждый модуль в сабпроцессе |

Раскладка зеркалит дерево исходников (`tests/mcp/...`, `tests/wiki/...`).
Общие хелперы: `tests/mcp/conftest.py` (фикстура `client` на SDK-дефолте
`mode="auto"`, то есть современный путь согласования протокола `2026-07-28`;
`create_test_settings`; `make_test_lifespan`) и `tests/aioresponses_utils.py`.
Поля протокольных моделей — snake_case (`structured_content`, `input_schema`);
camelCase работает как kwarg конструктора, но не для доступа к атрибутам.

**Требование к покрытию — 100%, и по стейтментам, и по веткам** (`--cov-branch
--cov-fail-under=100`, порог зашит в CI). Правила, которые делают эту цифру
честной, а не декоративной:

- Действительно недостижимая строка несёт `# pragma: no cover` **с причиной в
  комментарии** (сужение типов после `resolve_page_locator`, фолбэки
  сериализаторов, которые pydantic никогда не дёргает, недостижимый хвост
  retry-цикла).
- Никогда не удалять и не ослаблять тест ради зелёного прогона; закрывайте дыру
  или обосновывайте pragma.
- Блоки `if __name__ == "__main__":` и `TYPE_CHECKING` исключены глобально в
  `pyproject.toml`.

Поверх юнит-тестов есть **живой слой**: `scripts/contract_sweep.py` вызывает
каждый метод `WikiClient` на настоящей организации и репортит расхождения
валидации и необъявленные ключи. Он существует потому, что эндпоинт поиска
однажды молча сменил контракт (ещё в бытность недокументированности), и он же поймал `page_move` как
тихий no-op до того, как та тулза успела уехать в релиз. Он **пишет** в вики
под заданным базовым слагом — используйте черновое место в личном разделе.
Workflow `api-drift.yml` гоняет его еженедельно при настроенных секретах
`DRIFT_*`; находки складываются в [api-notes_ru.md](api-notes_ru.md).

## CI

`test.yml` гоняет три джобы на каждый push и PR:

- **lint** — `scripts/check_versions.py` (консистентность версий по релизным
  метаданным), ruff check, проверка ruff format, ty, mypy.
- **install** — собирает wheel и ставит его **со свежим резолвом
  зависимостей**, затем конструирует сервер и пересчитывает тулзы. Джоба
  существует потому, что всё остальное ставится из `uv.lock`, и диапазоны
  версий в `pyproject.toml` однажды не проверялись нигде — и 1.0.0 уехал
  неустанавливаемым в день, когда его SDK выпустил мажорную версию.
- **test** — pytest со 100%-гейтом по матрице ОС × Python (3.11–3.13);
  покрытие грузится в Codecov из одной ячейки.

`release.yml` триггерится на тег версии: валидирует метаданные, собирает
wheel, MCPB-бандл и Docker-образ, затем публикует (PyPI, GitHub-релиз, GHCR,
реестр MCP). `api-drift.yml` — еженедельный живой свип.

## Процесс релиза

Версии живут в **четырёх файлах плюс одной строке тега**: `pyproject.toml`,
`uv.lock` (перегенерировать, не править руками), `manifest.json`,
`server.json` (два поля `version` **и** тег OCI-образа — единственное, что
`check_versions.py` не покрывает). Релизный коммит, по конвенции озаглавленный
`Release vX.Y.Z`:

1. Бампнуть всё перечисленное; прогнать `uv lock`.
2. Превратить `## [Unreleased]` в `## [X.Y.Z] - дата` в `CHANGELOG.md`.
3. Дописать датированную запись в журнал исполнения ROADMAP.
4. Прогнать полный набор проверок, включая install-смоук
   (`uv build` → установка wheel в свежий venv → конструирование сервера).
5. Закоммитить, запушить, дождаться зелёного CI, затем
   `git tag vX.Y.Z && git push origin vX.Y.Z`.

С 1.0.0 поверхность тулзов — обещание совместимости: ломающие изменения
означают мажорный бамп. Публикация на PyPI необратима — тегайте только по
зелёному CI.

## Точки синхронизации между файлами

Вещи, которые нигде (или лишь частично) не проверяются автоматически и которые
надо синхронизировать руками:

- **Список тулзов**: `manifest.json` ↔ зарегистрированная поверхность — прибит
  тестом; таблицы тулзов в README и утверждения «32 тулзы» в обоих README —
  нет.
- **Семантика `page_search.content`**: описание поля в
  `wiki/proto/types/pages.py`, описание тулзы в `page_read.py` и
  `build_instructions()` — три копии, одна истина.
- **Описание сервера**: в рантайме берётся из метаданных пакета, но
  `manifest.json` и `server.json` несут собственные копии.
- **Двуязычные пары**: `README.md` ↔ `README_ru.md`, `api-notes.md` ↔
  `api-notes_ru.md`, этот файл ↔ `architecture.md`.
- **Поверхность env-переменных**: `settings.py` ↔ `.env.example` ↔ таблицы
  конфигурации в README ↔ user config в `manifest.json`.
