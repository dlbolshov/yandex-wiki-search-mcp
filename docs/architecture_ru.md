## Система с высоты птичьего полёта

`yandex-wiki-search-mcp` — MCP-сервер перед публичным HTTP API Яндекс Вики:
33 тулзы (10 на чтение, 23 на запись), 2 ресурса, три транспорта (stdio,
streamable HTTP, SSE) и один опциональный OAuth-слой для многопользовательских
HTTP-деплоев.

Вызов тулзы проходит такой путь:

```
MCP-клиент
  │  stdio / streamable-http / sse
  ▼
MCPServer (mcp_wiki/mcp/server.py)
  │  middleware: DEBUG-лог таймингов → запрос прячется в contextvar
  ▼
tool handler (mcp_wiki/mcp/tools/*)
  │  параметры через pydantic → get_yandex_auth() с per-request переопределением
  ▼
WikiClient (mcp_wiki/wiki/custom/client.py)
  │  заголовки ← select_org(); ретраи с бэкоффом; маппинг ошибок
  ▼
https://api.wiki.yandex.net
```

Ответ возвращается типизированной pydantic-моделью, сериализуется без
`None`-полей, валидируется по output-схеме тулзы и дублируется текстовым
блоком, чью подробность регулирует `TOOL_RESULT_TEXT`. Единственное
исключение — `page_read_attachment`: он зарегистрирован с
`structured_output=False`, output-схемы у него нет, и он возвращает один
контент-блок — `ImageContent` для опознанной картинки, иначе
`EmbeddedResource`, — который уходит один раз и который `TOOL_RESULT_TEXT`
не трогает.

## Два слоя

Пакет разделён на доменный слой и слой представления, и зависимость между ними
направлена строго в одну сторону:

- **`mcp_wiki/wiki/`** — домен Яндекс Вики. Асинхронный HTTP-клиент, модели
  ответов, таксономия ошибок, работа со слагами. Ничего не знает про MCP;
  обязан быть пригоден из обычного скрипта (и пригоден —
  `scripts/contract_sweep.py` использует его напрямую).
- **`mcp_wiki/mcp/`** — MCP-представление. Сборка сервера, тулзы, ресурсы,
  модели параметров, OAuth. Свободно импортирует Wiki-слой.

**Правило: `mcp_wiki.wiki` никогда не импортирует из `mcp_wiki.mcp`.** Это не
эстетика: одно нарушение однажды замкнуло цикл импортов через
`mcp_wiki.wiki.__init__`, из-за которого `import mcp_wiki.mcp.utils` падал с
`ImportError` при первом импорте, а тесты этого не видели, потому что
conftest уже импортировал пакет в рабочем порядке. `tests/test_imports.py`
импортирует каждый модуль в сабпроцессе, чтобы держать слоистость честной.
Если хелпер нужен обеим сторонам, он живёт в Wiki-слое, а `mcp_wiki.mcp.utils`
его реэкспортирует (прецедент — `normalize_slug`).

## Карта кода

### Точка входа и конфигурация

- **`mcp_wiki/__main__.py`** — собирает `Settings`, отказывается стартовать при
  подозрении на опечатку в окружении (см. ниже), настраивает логирование в
  stderr, логирует эффективную конфигурацию, затем
  `create_mcp_server(settings).run(transport, **run_options(settings))`.
- **`mcp_wiki/settings.py`** — pydantic-settings поверх переменных окружения и
  `.env`-файла. Два решения, которые стоит знать:
  - `extra="ignore"`: `.env` — директорная конвенция, общая с другими
    инструментами, поэтому посторонний `OPENAI_API_KEY` не должен
    останавливать этот сервер.
  - `suspicious_env_keys()`: защита от опечаток, которую раньше давала
    строгость, — починенная и расширенная на настоящие переменные окружения.
    Ключ внутри неймспейсов этого сервера (`WIKI_*`, `OAUTH_*`, `REDIS_*`,
    `MCP_*`, `TOOL_*`), difflib-близкий к реальному полю (`WIKI_READ_ONL`),
    останавливает старт с подсказкой did-you-mean; посторонние ключи
    (`REDIS_URL`) проходят.
  - Модельный валидатор следит за инвариантами: не больше одного из
    `WIKI_ORG_ID`/`WIKI_CLOUD_ORG_ID`, токен, пока OAuth выключен,
    OAuth-тройка, когда включён. Ровно один org id обязателен только при
    выключенном OAuth; под OAuth допустим ноль, потому что организация может
    прийти в запросе (`?orgId=`/`?cloudOrgId=`), поэтому
    `WikiClient._build_headers` перепроверяет её на каждом вызове и бросает
    `WikiConfigError` с обоими вариантами исправления.
    `include_local_uploads` — property, а не
    поле: `page_upload_attachment` и `page_download_attachment` читают и
    пишут файловую систему *сервера*, поэтому предлагаются только на stdio
    при выключенном OAuth — единственной схеме, где эта файловая система
    принадлежит вызывающему. По HTTP это контейнер или общий хост, а без
    OAuth эндпоинт не аутентифицирует никого, и диск сервера достался бы
    любому, кто достучался до порта.

### MCP-слой

- **`mcp_wiki/mcp/server.py`** — точка сборки. `create_mcp_server()` подключает
  lifespan, опциональные OAuth-провайдер и стор, инструкции, кэш-хинты,
  middleware, кастомные роуты (`/healthz`, OAuth-коллбэк), затем регистрирует
  ресурсы и тулзы. Четыре детали, которые кусаются:
  - `WikiMCPServer.call_tool` решает, что упавшая тулза скажет модели.
    Начиная с mcp 2.1 (python-sdk#3314) SDK передаёт текст ошибки только
    для `ToolError`. Всё остальное считается падением: сервер пишет его в
    лог с трейсбеком, а модель получает голое `Error executing tool
    <name>`. Поэтому тулзы отказывают на плохие аргументы через
    `ToolError`; `ValueError` остаётся только внутри pydantic-валидаторов,
    где SDK превращает его в ошибку аргументов. `WikiError` приходит из
    слоя, который не может импортировать SDK, поэтому `call_tool` поднимает
    его до `ToolError` с тем же текстом, что отправлял mcp 2.0. Любое
    другое исключение остаётся замаскированным — эту половину политики
    стоит сохранить. `uv.lock` пинит mcp 2.0.0, который передаёт любое
    сообщение, поэтому регрессию здесь видит только джоба
    `test-latest-mcp` (см. [CI](#ci)).
  - Ещё он постобрабатывает результаты для `TOOL_RESULT_TEXT`
    (`pretty`/`compact`/`none`), не трогая structured content.
  - Транспортные kwargs живут в `run_options()`/`http_app_options()`, а не в
    конструкторе — и **`host` обязан до них доходить**: SDK по умолчанию
    ставит loopback и автоматически взводит защиту от DNS rebinding, которая
    за настоящим hostname отвечает `421` на каждый MCP-запрос, пока `/healthz`
    продолжает говорить `200`.
  - `server_version()`/`server_description()` читают метаданные пакета, так
    что `pyproject.toml` остаётся единственным источником обоих.
- **`mcp_wiki/mcp/context.py`** — `AppContext`, полезная нагрузка lifespan:
  экземпляр `WikiProtocol` плюс базовый веб-URL.
- **`mcp_wiki/mcp/middleware.py`** — DEBUG-лог каждого входящего сообщения со
  временем обработки. Намеренно молчит на INFO: строка на каждый запрос
  подвесила бы stdio-сервер, чей клиент не вычитывает stderr.
- **`mcp_wiki/mcp/request_ctx.py`** — contextvar с транспортным запросом
  обрабатываемого сообщения. Существует потому, что SDK не инжектит `Context`
  в ресурс со статическим URI, а `wiki-mcp://configuration` нужна
  query-строка. `Server.middleware` апстримом помечен как provisional, поэтому
  этот модуль и `middleware.py` — сознательно единственные два места, которые
  его трогают.
- **`mcp_wiki/mcp/params.py`** — общие `Annotated`-типы параметров (ID, слаги,
  курсоры, `fetch_all`), модели тел запросов для операций с гридами и
  `build_instructions()`, которая выводит инструкции сервера из тех же
  настроек, что управляют регистрацией тулзов, — read-only сервер описывает только
  то, что зарегистрировал.
- **`mcp_wiki/mcp/utils.py`** — `get_yandex_auth()` (per-request
  переопределение токена и организации; предпочитает `Context` обработчика,
  откатывается на запрос из middleware) и `resolve_page_locator()` (контракт
  «ровно один из `page_id`/`slug`», общий для всех страничных тулзов).
- **`mcp_wiki/mcp/resources.py`** — два ресурса: `wiki-mcp://configuration`
  (сообщает пару организаций через тот же `select_org()`, что и клиент,
  поэтому не может отчитаться комбинацией, которую не несёт ни один запрос) и
  `wiki-mcp://yfm-cheatsheet`.
- **`mcp_wiki/mcp/tools/`** — `page_read.py` (10 читающих тулзов),
  `page_write.py` (23 пишущих; регистрируются только при
  `WIKI_READ_ONLY=false`, а локально-файловая пара —
  `page_upload_attachment`, `page_download_attachment` — только на stdio
  при выключенном OAuth), `common.py` (резолв локатора через живой API, когда
  слаг должен стать id или наоборот). Пишущие тулзы прикладывают
  неблокирующие `yfm_warnings` из `mcp_wiki/yfm.py`.
- **`mcp_wiki/yfm.py`** — YFM-линт без зависимостей (только предупреждения,
  никогда не блокирует запись) и текст шпаргалки. Правила кодируют живое
  поведение рендерера (`scripts/yfm_smoke.py`).

### OAuth-подсистема (`mcp_wiki/mcp/oauth/`)

Опциональна; собирается только при `OAUTH_ENABLED=true`. Сервер тогда
выступает OAuth authorization server для MCP-клиентов и проксирует реальную
идентичность в Яндекс OAuth:

```
клиент → /authorize ──► редирект на oauth.yandex.ru (ключ: серверный state_id)
Яндекс → /oauth/yandex/callback ──► забрать state, выпустить mcp_-код с кодом Яндекса внутри, редирект клиенту
клиент → /token ──► наш код → обмен в /token Яндекса → пара access/refresh, хранится под хэшированными ключами
```

На коллбэке код Яндекса не обменивается: он едет внутри нашего кода
авторизации, пока клиент не предъявит его на `/token`, и только тогда
`exchange_authorization_code()` обращается к Яндексу. Ключи токенов — хэши
SHA-256; в значениях при этом лежит сам токен — в памяти процесса у
memory-стора, зашифрованный Fernet у Redis.

- **`provider.py`** — поток выше. Ключ хранения pending-авторизации всегда
  генерирует сервер (`secrets.token_hex`); клиентский `state` — данные,
  которые эхом возвращаются на финальном редиректе, и никогда не ключ.
  Нарушение этого правила было CVE-образным: предсказуемый ключ позволял
  атакующему перезаписать pending-запись и забрать код жертвы, включая PKCE.
  Отказ `/token` Яндекса (любой не-200, при обмене кода или refresh)
  поднимается как `TokenError(invalid_grant)` со статусом и ошибкой Яндекса
  и пишется в лог warning'ом: это единственное исключение, которое
  `TokenHandler` SDK превращает в OAuth-ошибку 400, а всё прочее доходит до
  клиента голым 500. При обмене кода `invalid_grant` верен при любой
  причине отказа: загрузка `mcp_`-кода уже его израсходовала.

  Провайдер же решает, сколько живёт динамическая регистрация: `/register`
  не аутентифицирован, и всё, что он хранит вечно, можно забить нарочно.
  Конфиденциальный клиент уходит вместе с секретом: SDK проставляет
  `client_secret_expires_at` из `OAUTH_CLIENT_SECRET_EXPIRY_SECONDS`,
  сообщает его клиенту и отвергает секрет после него (`0`, который
  проставляется при выключенном сроке, — это «никогда» из RFC 7591).
  Публичному клиенту (`token_endpoint_auth_method: none`) секрет не выдаётся,
  так что SDK ничего не проставляет и ничего не проверяет; провайдер даёт ему
  ту же настройку как окно простоя, которое перезапускается после каждого
  успешного обмена кода или refresh и никогда не короче только что выданного
  refresh-токена. Фиксированный срок без предупреждения снимал бы
  регистрации, которыми пользуются, — в RFC 7591 нет поля, чтобы его
  объявить, — а собственный клиент SDK отвечает на получившийся
  `invalid_client`, снова открывая `/authorize` с мёртвым `client_id`, и
  пользователь застревает на странице «Client ID not found».
- **`store.py`** — протокол `OAuthStore` и общий `REFRESH_TOKEN_TTL_SECONDS`
  (31 день, срок жизни refresh-токена Яндекса). `save_client` получает TTL
  от провайдера, как `save_state` и `save_auth_code`; ни один стор не читает
  срок из записи клиента, так что прочитать его по-разному они не могут.
- **`stores/memory.py`** — dict-стор для однопроцессных деплоев. Раз
  `/authorize` и `/register` не аутентифицированы, всё истекаемое несёт
  дедлайн, а записи запускают амортизированный sweep (порог перенацеливается
  на удвоенный выживший размер), так что брошенные логины не могут раздувать
  процесс безгранично. Регистрации тоже: `get_client` сам отвергает
  истёкшую, не дожидаясь sweep, — Redis к этому моменту уже удалил ключ.
  У публичного клиента SDK срок не проверяет вовсе, у конфиденциального —
  только на `/token`, и иначе `/authorize` провёл бы пользователя через весь
  логин в Яндексе лишь затем, чтобы отказать в конце.
- **`stores/redis.py`** — продакшн-стор. Хэшами SHA-256 являются только
  ключи access, refresh и маппинга refresh→access; ключи клиента, state и
  кода авторизации — сырые идентификаторы. Шифрование на уровне полей
  (`crypto.py`, версионированные ключи для ротации через
  `OAUTH_ENCRYPTION_KEYS`, обязательные для Redis-стора) покрывает ровно поля
  `token` и `client_secret` (`serializers.py`), так что pending-state и
  запись кода авторизации — вместе с обёрнутым `yandex_auth_code` — лежат
  открытым текстом свои 600 с / 300 с TTL. TTL делегированы Redis, включая
  TTL регистраций клиентов (при пустом `OAUTH_CLIENT_SECRET_EXPIRY_SECONDS`
  регистрация живёт без TTL). Одноразовые записи — state и код авторизации —
  забирает `DEL`, а не `GET`: два конкурентных погашения могут оба прочитать
  запись, но получит её только тот, чей `DEL` удалил ключ.
- **`types.py`** — pydantic-формы записей state, callback и кода.

Весь поток, нарисованный по коду в двух частях: регистрация и вход, затем
обмен кода, вызов с Bearer и обновление токена:

### Wiki-слой (`mcp_wiki/wiki/`)

- **`proto/pages.py`** — `WikiProtocol`, интерфейс, против которого
  программируют тулзы. Тулзы никогда не видят `WikiClient` напрямую; тесты
  подставляют `AsyncMock` с поверхностью этого протокола.
- **`proto/common.py`** — `YandexAuth` (per-request учётные данные) и
  `select_org()`: per-request auth заменяет организацию **целиком**, никогда
  не смешивая `cloud_org_id` запроса с серверным `org_id`. Клиент строит из
  него заголовки, а ресурс конфигурации из него же отчитывается, так что
  разъехаться они не могут.
- **`proto/types/pages.py`** — модели ответов. `BaseWikiModel` выбрасывает
  `None`-поля при сериализации (экономия токенов в выводе для LLM) и вычищает
  шум `title` из генерируемых JSON-схем; `DynamicWikiModel` вдобавок сохраняет
  неизвестные ключи при round-trip. Формы ячеек/строк/колонок гридов тоже
  живут здесь.
- **`custom/client.py`** — `aiohttp`-клиент. Единая воронка `_request_raw()`
  применяет auth-заголовки (схема `OAuth`/`Bearer`, IAM или per-request
  токен), заголовки организации через `select_org()`, ретраит то, что
  безопасно повторить, и маппит сбои в таксономию ошибок. Ретраибельны по
  умолчанию GET, плюс два вызова с `retryable=True` (`POST v1/search`,
  `PUT upload_part`), минус GET'ы скачивания вложений, где повтор заново
  перекачивает весь файл; ретраятся только обрывы соединения и
  `429`/`502`/`503`/`504`, никогда таймауты (экспоненциальный бэкофф с equal
  jitter; `Retry-After` в пределах потолка побеждает, более длинный —
  немедленная ошибка). Гридовый `409 CONFLICTING_OPERATION` не ретраится:
  отклонённая мутация не применена, и наружу выходит `GridConflict` с
  рецептом восстановления в сообщении. Она же несёт потолок на тело
  ответа (выбирается по Content-Type ответа — download-эндпоинт не шлёт
  Content-Length) и `body_sink`, который стримит ответ прямо в переданный
  потребитель, минуя память; `_request()` — тонкая обёртка «только байты»
  для остальных эндпоинтов. Также владеет многошаговыми флоу: upload-сессии
  (create → parts → finish → attach), поллинг отложенной операции
  `page_clone` и атомарная запись загрузки на диск (`.part` → fsync →
  link/replace). Последняя выполняет все шаги по файловой системе на одном
  воркер-треде на вызов: дескриптор никогда не трогается с event loop,
  поэтому отменённый `await` не может закрыть его, пока другой тред туда
  пишет, а очистка, поставленная в очередь за незавершённым открытием,
  видит итоговое состояние, а не гоняется с ним.
- **`custom/errors.py`** — таксономия. `WikiError` → `WikiApiError`
  (HTTP-уровень, `build_api_error()` выбирает подкласс; `GridConflict` для
  гридового лока) плюс `PageNotFound`/`GridNotFound`/`AttachmentNotFound`
  (последний маппится в клиенте, потому что download-эндпоинт отвечает на
  промах GIF-заглушкой, а не JSON-конвертом ошибки), `WikiOperationError`
  (отложенная операция провалилась *после* того, как каждый HTTP-обмен
  удался), `WikiTransportError` (таймауты и сбои соединения, с непустым
  сообщением даже для `TimeoutError`), `ResponseTooLarge` (тело больше
  потолка `max_bytes` вызывающего — отказ по `Content-Length` до чтения или
  на байт за потолком в потоке, который длину не объявил),
  `WikiLocalFileError` (локальный путь, которым тулзы вложений не могут
  воспользоваться; исходный `OSError` хранится в `cause`), `WikiConfigError`
  (кривая настройка сервера), `WikiArgumentError` (запрос, который клиент
  отказывается отправлять: `cursor` поиска без `highlight`, пустая цель
  клонирования, обновление страницы, которое не просит ничего или просит
  противоположного; заодно это `ValueError`). Любая ошибка, которую должен
  прочитать вызывающий, — это `WikiError`, и MCP-слой на это опирается,
  чтобы показать её текст.
- **`custom/mimes.py`** — `image_mime()`: четыре формата, которые vision API
  умеет декодировать (PNG/JPEG/GIF/WebP), опознаются по magic-байтам и никогда
  по `Content-Type` с провода. Живёт в Wiki-слое, потому что нужен обоим путям
  вложений — чтению в диалог, чтобы решить, можно ли отдать байты image-блоком,
  и записи на диск, чтобы `mimetype` совпадал, — а импортировать MCP-слой отсюда
  нельзя.
- **`custom/slugs.py`** — `normalize_slug()`: полный URL Вики или слаг → голый
  слаг. Живёт здесь, потому что клиенту он нужен на каждом страничном вызове
  (см. правило слоёв).
- **`custom/anchors.py`** — запасной путь для `anchor` у
  `page_append_content`: когда API отвечает `ANCHOR_NOT_FOUND`, клиент сам
  вставляет текст после якоря в сырой разметке и сохраняет страницу через
  `page_update`. Находит только явные якоря — `{#id}` у заголовка, инлайновый
  `#[text](id)`, макрос `{{anchor href="id"}}`; заголовок без `{#id}` якорем
  не считается.

## Один контракт API, на который стоит обратить внимание

`GET /pages/descendants?slug=` с **пустым** слагом означает «вся организация» —
осознанный контракт API, а не небрежная обработка ввода (неразрешимый слаг
даёт 404; пропуск параметра — 400). Проверено вживую 2026-08-10, см.
[api-notes_ru.md](api-notes_ru.md). `page_get_descendants(from_root=true)` —
единственный, кто его шлёт. Не «чините» пустой слаг в
`WikiClient.page_get_descendants`; `resolve_page_locator` по-прежнему отклоняет
его для всех остальных тулзов, где API действительно нужна страница.

## Тестирование

Тесты используют моки на каждом шве, который задаёт архитектура:

| Шов | Техника |
|---|---|
| MCP-протокол ↔ тулзы | in-memory `Client` из SDK против настоящего `MCPServer`; тулзы видят `AsyncMock` `WikiProtocol` |
| тулзы ↔ Wiki-клиент | контракт — `WikiProtocol`; у пишущих тулзов проверяются точные аргументы вызовов |
| Wiki-клиент ↔ HTTP | `aioresponses`; ассерты на заголовки, query-параметры и тела в том виде, как их отправил бы aiohttp |
| OAuth ↔ Redis | `fakeredis` |
| пакет ↔ интерпретатор | `tests/test_imports.py` импортирует каждый модуль в сабпроцессе |
| Docker-образ ↔ CI ↔ uv | `tests/test_dockerfile.py`: пин uv в Dockerfile точный, каждый шаг `setup-uv` пинит тот же релиз, `required-version` остаётся нижней границей и `uv.toml` её не перекрывает (см. [Инструментарий](#инструментарий)) |

Раскладка зеркалит дерево исходников (`tests/mcp/...`, `tests/wiki/...`).
Общие хелперы: `tests/mcp/conftest.py` (фикстура `client` на SDK-дефолте
`mode="auto"`, то есть современный путь согласования протокола `2026-07-28`;
`create_test_settings`; `make_test_lifespan`) и `tests/aioresponses_utils.py`.
Поля протокольных моделей — snake_case (`structured_content`, `input_schema`);
camelCase работает как kwarg конструктора, но не для доступа к атрибутам.

**Требование к покрытию — 100%, и по стейтментам, и по веткам**
(`--cov-branch`; CI проверяет порог на ubuntu — почему не везде, см.
[CI](#ci)). Правила, которые делают эту цифру честной, а не декоративной:

- Действительно недостижимая строка несёт `# pragma: no cover` **с причиной в
  комментарии** (сужение типов после `resolve_page_locator`, фолбэки
  сериализаторов, которые pydantic никогда не дёргает, недостижимый хвост
  retry-цикла).
- Никогда не удалять и не ослаблять тест ради зелёного прогона; закрывайте дыру
  или обосновывайте pragma.
- Блоки `if __name__ == "__main__":` и `TYPE_CHECKING` исключены глобально в
  `pyproject.toml`.

Поверх юнит-тестов есть **живой слой**: `scripts/contract_sweep.py` вызывает
каждый метод `WikiClient` на настоящей организации и репортит расхождения
валидации и необъявленные ключи. Он существует потому, что эндпоинт поиска
однажды молча сменил контракт (ещё в бытность недокументированности), и он же поймал `page_move` как
тихий no-op до того, как та тулза успела уехать в релиз. Он **пишет** в вики
под заданным базовым слагом — используйте черновое место в личном разделе.
Workflow `api-drift.yml` гоняет его еженедельно при настроенных секретах
`DRIFT_*`; находки складываются в [api-notes_ru.md](api-notes_ru.md).

## CI

`test.yml` гоняет четыре джобы на каждый push и PR:

- **lint** — `scripts/check_versions.py` (консистентность версий по релизным
  метаданным), ruff check, проверка ruff format, ty, mypy.
- **install** — собирает wheel и ставит его **со свежим резолвом
  зависимостей**, затем конструирует сервер и пересчитывает тулзы. Джоба
  существует потому, что всё остальное ставится из `uv.lock`, и диапазоны
  версий в `pyproject.toml` однажды не проверялись нигде — и 1.0.0 уехал
  неустанавливаемым в день, когда его SDK выпустил мажорную версию.
- **test-latest-mcp** — весь набор тестов с mcp, поднятым до новейшего
  релиза, который разрешает диапазон (`uv sync --dev --upgrade-package mcp`;
  mcp-types едет следом, всё остальное остаётся залоченным). `uv.lock` пинит
  mcp 2.0.0 — нижнюю границу диапазона, так что `test` покрывает этот край,
  а эта джоба — тот, что получают пользователи `uvx` и `pip`. Она
  существует потому, что mcp 2.1.0 изменил то, что упавшая тулза показывает
  модели (см. `WikiMCPServer.call_tool` выше): 43 теста падали на нём и
  проходили на локе, а `install` только пересчитывает тулзы.
- **test** — pytest по матрице ОС × Python (3.11–3.13); покрытие грузится в
  Codecov из одной ячейки матрицы. **100%-гейт проверяется только на
  ubuntu**, отдельным шагом `coverage report --fail-under=100`. Windows и
  macOS гоняют все тесты, которые могут, но несколько тестов — и код,
  который покрывают только они, — есть лишь на POSIX (биты прав, `fchmod`,
  fsync дескриптора каталога). На Windows эти строки недостижимы, так что
  гейт там можно было бы удовлетворить, только исключив их из измерения
  на всех ОС сразу — а вместе с измерением прячутся и настоящие
  регрессии. Гейт стоит там, где достижим весь код, а `# pragma: no cover`
  остаётся для настоящих платформенных развилок.

`release.yml` триггерится на тег версии и на ручной `workflow_dispatch`:
валидирует метаданные, собирает wheel и MCPB-бандл, собирает **и пушит**
Docker-образ в GHCR; джоб `publish` (PyPI, GitHub-релиз, реестр MCP) затем
выполняется только на пуше тега. Пуш в GHCR за этим условием не стоит — он
происходит в `build-docker` на каждом запуске, так что ручной запуск всё
равно пушит образ с тегом от ref'а, на котором он шёл (`:main` с main), а на
теге образ уходит раньше, чем начинается публикация на PyPI. `api-drift.yml`
— еженедельный живой свип.

`pages.yml` выкладывает `docs/diagrams/` на GitHub Pages при пуше в main,
который её затрагивает, или вручную. Он ничего не собирает: HTML лежит в
репозитории и пересобирается локально (см. [Диаграммы](#диаграммы)).

## Процесс релиза

Версии живут в **четырёх файлах плюс одной строке тега**: `pyproject.toml`,
`uv.lock` (перегенерировать, не править руками), `manifest.json`,
`server.json` (два поля `version` **и** тег OCI-образа — единственное, что
`check_versions.py` не покрывает). Релизный коммит, по конвенции озаглавленный
`Release vX.Y.Z`:

1. Бампнуть всё перечисленное; прогнать `uv lock`.
2. Превратить `## [Unreleased]` в `## [X.Y.Z] - дата` в `CHANGELOG.md`.
3. Дописать датированную запись в журнал исполнения ROADMAP.
4. Прогнать полный набор проверок, включая install-смоук
   (`uv build` → установка wheel в свежий venv → конструирование сервера).
5. Закоммитить, запушить, дождаться зелёного CI, затем
   `git tag vX.Y.Z && git push origin vX.Y.Z`.

С 1.0.0 поверхность тулзов — обещание совместимости: ломающие изменения
означают мажорный бамп. Публикация на PyPI необратима — тегайте только по
зелёному CI.

## Точки синхронизации между файлами

Вещи, которые нигде (или лишь частично) не проверяются автоматически и которые
надо синхронизировать руками:

- **Список тулзов**: `manifest.json` ↔ зарегистрированная поверхность — прибит
  тестом; таблицы тулзов в README и утверждения «33 тулзы» в обоих README —
  нет.
- **Семантика `page_search.content`**: описание поля в
  `wiki/proto/types/pages.py`, описание тулзы в `page_read.py` и
  `build_instructions()` — три копии, одна истина.
- **Капы на вложения**: `MAX_INLINE_ATTACHMENT_BYTES` и
  `MAX_INLINE_IMAGE_BYTES` в `mcp/tools/page_read.py` — источник истины;
  описание тулзы подставляет их f-строкой, но оба README, оба `api-notes` и
  `manifest.json` пересказывают числа прозой. Понизишь константу — пять
  документов продолжат рекламировать лимит, которого больше нет.
- **Описание сервера**: в рантайме берётся из метаданных пакета, но
  `manifest.json` и `server.json` несут собственные копии.
- **Двуязычные пары**: `README.md` ↔ `README_ru.md`, `api-notes.md` ↔
  `api-notes_ru.md`, этот файл ↔ `architecture.md`.
- **Поверхность env-переменных**: `settings.py` ↔ `.env.example` ↔ таблицы
  конфигурации в README ↔ user config в `manifest.json`.
- **Диаграммы**: `docs/diagrams/src/{en,ru}/*.json` описывают код на
  коммите из их `meta.repository.revision`, и с более поздним кодом их никто
  не сверяет. Изменение того, что показывает диаграмма, — это правка обоих
  языковых исходников и пересборка, см. [Диаграммы](#диаграммы).

## Диаграммы

В `docs/diagrams/` лежат пять диаграмм [Archify](https://github.com/tt-a1i/archify)
на английском и русском: архитектура рантайма, один вызов `page_edit`,
проверки и листание `page_search` и OAuth-поток в двух частях. `pages.yml`
публикует папку на **https://dlbolshov.github.io/yandex-wiki-search-mcp/**; индексная страница переключает диаграммы и
язык.

- `src/<lang>/<name>.json` — источник истины: типизированный JSON Archify,
  где каждый блок ссылается на диапазоны строк репозитория на одном
  закреплённом коммите (`meta.repository`).
- `<lang>/<name>.html` — проверенная самодостаточная интерактивная
  диаграмма: зум, поиск, связи вверх и вниз по потоку, построение маршрута,
  светлая и тёмная темы, экспорт и процитированные строки каждого блока на
  GitHub в один клик.
- `<lang>/<name>.svg` — собственный экспорт вьюера «SVG · Авто», который
  следует светлой или тёмной теме читателя; их встраивает этот файл.

Чтобы изменить диаграмму, правьте оба языковых исходника — если код сдвинулся,
то и процитированные диапазоны с `meta.repository.revision`, которая должна
быть запушенным коммитом, — и запускайте
`uv run python scripts/build_diagrams.py [name] [--lang en|ru]`. Для каждого
исходника он прогоняет `finalize` Archify (схема, раскладка, сверка ссылок на
код с этим коммитом, проверка в настоящем браузере), копирует HTML и заново
экспортирует SVG через headless Chrome. Нужны один раз установленный Archify
(`npx skills add tt-a1i/archify -g`, Node 18+) и Chrome или Chromium в
`PATH`; ни то, ни другое не зависимость проекта, и CI диаграммы не собирает.
Коммитьте исходники, HTML и SVG вместе.

## Инструментарий

`uv` для всего (sync, lock, build, run), `Taskfile.yml` для шорткатов
(`task` = lock + format + check + test; `task test-cov` = CI-гейт плюс
HTML-отчёт), ruff (линт + формат), mypy **и** ty (два тайпчекера — ty как
второе мнение), pytest + pytest-asyncio. Python 3.11–3.13. Пакет поставляет
`py.typed`.

Версия самого uv закреплена дважды и ограничена один раз. Образ uv в
Dockerfile и каждый шаг `setup-uv` в CI (`version:`) называют один и тот же
точный релиз, так что образ собирается и CI тестирует одним известным uv.
Плавающий тег исключён: `:latest` сломал сборку образа, когда стал uv 0.13.0,
а собирает образ только `release.yml`, так что до релиза этого никто бы не
заметил. `[tool.uv] required-version` в `pyproject.toml` — только нижняя
граница. uv проверяет её почти в любой команде внутри копии этого дерева
(кроме `uvx`/`uv tool` и `uv self`): в чекауте контрибьютора, в
распакованном бандле Claude Desktop (его `uv run`) и у сборщиков, которые
ставят из исходников, вроде glama.ai. Потолок `<0.13`, добавленный в 1.5.0,
сломал их всех в день выхода uv 0.13.0, а ломающий минор uv выпускает
примерно раз в три месяца. `tests/test_dockerfile.py` падает, если пины
разошлись, если у диапазона появился потолок или если его перекрывает
появившийся `uv.toml`. Переход на новый uv — это тег образа и пять входов
`version:` в одном изменении.

Интерпретатор бандла выбирает uv пользователя, поэтому `manifest.json`
ограничивает его через `UV_PYTHON` (3.11–3.14) в `mcp_config.env`. С 0.13 uv
скачивает Python 3.15 везде, где нет подходящего интерпретатора, а у
нескольких залоченных пакетов (`cffi`, `pydantic-core`, `aiohttp`, `rpds-py`)
нет колёс под 3.15. Поднимайте эту границу, когда до неё дорастёт lock.
