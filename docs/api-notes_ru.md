# Yandex Wiki API: полевые заметки

Находки проверены живьём на продакшн-организации Яндекс 360. Org-нейтральные
probe-скрипты в [`scripts/`](../scripts/) — живая документация этого поведения,
их можно перезапустить на своей организации: `probe_api*.sh`/`smoke.sh` (на curl;
креды через env-переменные или файл `$SECRETS`, вывод идёт в `raw/`, который в
gitignore, потому что содержит реальные данные организации), плюс Python-пробы
`contract_sweep.py` (все методы клиента против живого API), `token_probe.py`
(размеры ответов и лишние поля) и `yfm_smoke.py` (правила рендеринга YFM).

**Внимание: недокументированные части API дрейфуют.** Эндпоинт поиска молча сменил
wire-контракт между 2026-07-19 и 2026-08-02 (см. ниже) — без версионирования и
deprecation. Если что-то выглядит странно — перезапустите пробы, прежде чем верить
этим заметкам. Workflow [API drift check](../.github/workflows/api-drift.yml)
еженедельно перегоняет контракт-свип на живой организации, если настроены его
`DRIFT_*`-секреты.

## Эндпоинт поиска (`POST /v1/search`)

Эндпоинт недокументирован, но публичен — это тот же бэкенд, что обслуживает строку
поиска в веб-интерфейсе Вики. Первым его обнаружил и опубликовал
[slartus/mcp-yandex-wiki](https://github.com/slartus/mcp-yandex-wiki), что напрямую
вдохновило `page_search`; здесь эти находки независимо перепроверены и расширены.

**Wire-контракт молча изменился между 2026-07-19 и 2026-08-02.** По июльским пробам:
`page_size` управлял числом результатов (потолок 50, вне диапазона → 400), envelope
содержал `total_documents`/`total_pages`, `modified_at` был epoch-числом, а сниппет
лежал в ключе `body`. Ничего из этого больше не верно. Текущее поведение, проверено
2026-08-02:

- Числом результатов управляет **`limit` в теле POST**: 1–50, всё остальное → HTTP 400.
  `page_size`, `page` и `offset` принимаются, но **игнорируются** (получите дефолтные
  10 результатов). Тулза называет аргумент так же — `limit` (переименован из
  `page_size` в 1.0.0), ограничивая до 1–50.
- Envelope — `results` + `next_cursor`/`prev_cursor`. Курсоры **всегда `null`**, а
  `cursor` в запросе валидируется (мусор → 400), но удовлетворить его нечем — механика
  пагинации существует только в схеме. Вы получаете топ ≤50 совпадений, и всё.
  `total_documents`/`total_pages` исчезли.
- В результате: сниппет в **`content`** (плейн-текст), `modified_at` — **ISO-строка
  даты-времени**. Результаты двух типов: **`page`** (относительный `url`; тулза
  нормализует его в абсолютную ссылку на базе `WIKI_WEB_BASE_URL`) и **`file`**
  (абсолютная ссылка на скачивание `...?download=1`).
- Размер, замер `scripts/token_probe.py` от 2026-08-04 при `limit=50`: ответ на 48
  совпадений — около 28k символов, из них ~14k приходится на сниппеты; 33 сниппета
  из 48 длиннее 200 символов. Это стоит учитывать, поднимая `limit`: после
  фикса 0.8.0 (эндпоинт слушает `limit`) полноразмерный поиск стал примерно
  в 5 раз тяжелее прежних ответов на 10 результатов.
- Серверной фильтрации по-прежнему **нет** — body-параметры секций/типов игнорируются.
  Аргументы тулзы `slug_prefix` и `result_type` применяются на клиенте после получения.
- Запросы `"в кавычках"` работают и дают фразовый поиск; `-минус` и булевы операторы игнорируются.

## Авторизация, скоупы и права

- **OAuth-скоупы Wiki API не проверяет** — токен только с `wiki:read` всё равно может
  писать. Read-only гарантируется только нерегистрацией write-тулзов
  (`WIKI_READ_ONLY=true`). *Credit: первым публично сообщил
  [slartus/mcp-yandex-wiki](https://github.com/slartus/mcp-yandex-wiki), здесь подтверждено независимо.*
- **HTTP 403 — про права пользователя**, а не про скоупы токена: например, readonly
  системные страницы, принадлежащие `yandex360-wiki` (по slartus, см. выше).
- Источника заголовка организации два: `X-Org-Id` (Яндекс 360) и `X-Cloud-Org-Id`
  (Yandex Cloud); сервер выставляет один из них по `WIKI_ORG_ID`/`WIKI_CLOUD_ORG_ID`.

## Страницы

- **Любой `POST /pages/{id}` обновляет `modified_at`**, даже с пустым телом — страница
  помечается изменённой (по slartus, см. выше).
- **API ревизий/истории/обратных ссылок нет** — сценарии «кто ссылается сюда» невозможны.
- `created_at`/`modified_at`/`comments_count`/`is_readonly` — не топ-левел поля страницы;
  их нужно запрашивать через `page_get` с `fields=["attributes"]`.
- `GET /pages/{id}/resources?q=` — единственный серверный *текстовый* фильтр во всём API
  (поиск по названию среди вложений/гридов одной страницы) — доступен через `page_get_resources`.
- `page_type` в `POST /pages` **игнорируется** — любое значение, даже мусор, даёт
  `wysiwyg`-страницу без ошибки (проверено 2026-07-27).
- **Move/rename не существует** (живые пробы 2026-08-08). `POST /pages/{id}` с полем
  `slug` отвечает 200 и **молча игнорирует его** — документированное тело апдейта:
  `title`/`content`/`redirect`/`access_policy`/`owner`, без slug. Эндпоинта `/move`
  нет ни в v1, ни в v2 (404). Перенос страницы — возможность только веб-интерфейса.
  Остерегайтесь MCP-серверов, рекламирующих «move» поверх этого API: реализованный
  через `POST /pages/{id}` он — тихий no-op, сообщающий об успехе.
- **`POST /pages/{id}/clone` — единственный примитив переноса** — отложенная операция
  (`operation.id` + `status_url`; поллинг `GET /operations/clone/{id}` доходит до
  `status: "success"` примерно за секунду). Копия получает **новый page id**, переносит
  только заголовок и содержимое, **дети не следуют** (проверено 2026-08-08: `src/kid`
  не появился под `dst/`). Комментарии, вложения и история остаются у оригинала.
  Коллизии слагов отклоняются сразу на POST c `SLUG_OCCUPIED` (400), до старта
  операции. Доступно как `page_clone`: тулза поллит операцию и возвращает id и slug
  копии.
- `POST /pages/{id}/append-content` отвечает **полным объектом обновлённой страницы**
  (id, content, breadcrumbs, данные доступа, owner…), а не статус-заглушкой.
- Элементы descendants несут **только `id` и `slug`** — без заголовков; query-параметр
  `fields` принимается, но не работает. Курсорная пагинация работает (проверено
  обходом с `page_size=5`).
- `GET /pages/descendants` возвращает **всё поддерево, все уровни вложенности** одним
  плоским списком — не только прямых детей (проверено 2026-08-03: дерево в 3 уровня
  приходит одним вызовом). Параметра глубины нет; иерархия закодирована в слагах,
  глубина = `slug.count("/")` относительно корня.
- Удаление → восстановление (`DELETE /pages/{id}` → `POST /recovery_tokens/{token}/recover`)
  возвращает страницу с **тем же id**; в ответе recover дополнительно приходят `slug` и
  `pages_count` (размер поддерева).
- У объектов вложений есть недокументированный флаг `is_downloadable`.
- Удаление страницы **сразу освобождает слаг**: страница перестаёт открываться, и
  тот же слаг можно создать заново, хотя удаление и восстановимо по токену
  (проверено 2026-08-05).

## Комментарии

- Объекты комментариев несут `author` (id, логин, отображаемое имя), `inline_text`,
  `is_deleted`, `reactions` и `resolve_status`. Ключа **`user` нет** (по состоянию на
  2026-08-02 — ранние версии этого проекта его моделировали).
- Курсорная пагинация `GET /pages/{id}/comments` работает (проверено обходом с `page_size=2`).

## Гриды

- Эндпоинты мутаций гридов используют optimistic locking: требуют актуальную `revision`
  и отклоняют запрос, если она устарела.
- Wire-формат `default_sort` — список словарей с одним ключом, например
  `[{"status": "asc"}]`. Тулза `grid_update` принимает более дружелюбный формат
  `[{"column": "status", "direction": "asc"}]` и конвертирует его сама.
- `grid_add_columns` требует `required` у каждой колонки — API это валидирует.
- `grid_copy` асинхронный: API возвращает метаданные операции, а не готовую копию грида.
- Мутации гридов **сериализуются на грид**: вторая, отправленная пока первая ещё не
  улеглась, получает `409` `CONFLICTING_OPERATION` («Conflicting operation in
  progress») и **не применяется**, поэтому повтор после паузы безопасен. Замер
  2026-08-05, по 8 пар на каждый интервал: подряд ловится примерно в трети случаев и
  отпускает через ~10 с; при паузе 3 с и 10 с не сработало ни разу. Асинхронный
  `grid_copy` исходный грид **не блокирует** — мутация сразу после него проходит.
  `scripts/contract_sweep.py` повторяет конфликты, а не репортит блокировку как дрейф.
- `POST /grids/{id}/cells` отвечает ключом **`cells`** — в отличие от мутаций строк и
  колонок, которые отвечают `results` (+ `revision`).

## Ошибки и лимиты

- Ошибки приходят в **двух форматах envelope** (`message` строка-или-null плюс
  `details`, либо список плюс `level`); клиент парсит оба и пробрасывает собственное
  сообщение API в `WikiApiError`.
- Заголовков rate-limit нет (`X-RateLimit-*`/`Retry-After` отсутствуют).
